# MultiStack SDK — RKE2Cluster / RKE2Node / RKE2Backend

Real class signatures (from `multistack.core.rke2` and
`multistack.backends.rke2_client`, re-exported at the top level as
`from multistack import RKE2Cluster, RKE2Node`). This is the *only*
resource this skill covers — the SDK has since grown other resources
(Storage, MinIO, vLLM) that this agent doesn't have tools for yet; don't
assume this skill's rules apply to them. There is no GPU-type or region
field on a cluster itself, unlike what earlier planning documents
assumed. A cluster is a flat list of nodes, each provisioned over SSH
(or locally, for 127.0.0.1/localhost/::1).

`RKE2Node`/`RKE2Cluster` are Pydantic models, and `build_rke2_cluster_plan`'s
`nodes` parameter is typed as `list[RKE2Node]` directly — the field-by-field
shape below is generated straight from these classes for the tool schema a
model actually receives, not retyped by hand. What's below is for a human
reader; it can't drift out of sync with the tool's own schema the way a
hand-written description could.

```python
class RKE2Node(BaseModel):
    address: str
    user: str = "root"
    role: str = "server"          # "server" or "agent"
    ssh_key: Optional[str] = None
    ssh_port: int = 22

class RKE2Cluster(BaseModel):
    name: str
    version: str = "v1.33.1+rke2r1"
    nodes: List[RKE2Node] = Field(default_factory=list)
    token: Optional[str] = None                # auto-generated by create() if omitted
    kubeconfig_path: Optional[str] = None
    cni: str = "canal"             # "canal" | "cilium" | "calico" | "flannel" | "none"
    disable_kube_proxy: bool = False   # only valid when cni == "cilium"
    cilium_mtu: Optional[int] = None   # 576-9000, only valid when cni == "cilium"; leave unset unless the network path needs it
    pin_node_ip: bool = True           # make each node's declared address authoritative; leave True unless you have a reason not to

    def validate(self) -> None: ...   # runs automatically at construction and on any later assignment -- raises ValueError on:
        # - no nodes
        # - no "server" role node
        # - invalid role (must be "server" or "agent")
        # - invalid cni
        # - disable_kube_proxy=True with cni != "cilium"
        # - cilium_mtu set with cni != "cilium", or outside 576-9000
        # - duplicate node addresses

class RKE2Backend:
    def create(self, cluster: RKE2Cluster) -> str: ...             # returns kubeconfig; fails if state already exists
    def update(self, cluster: RKE2Cluster) -> str: ...              # reconciles running cluster; fails if no state exists
    def delete(self, cluster: RKE2Cluster | str) -> None: ...       # accepts either the object or just cluster.name
    def check_prerequisites(self, nodes, all_nodes=None) -> list[str]: ...  # called automatically inside create()/update()
```

Rules when generating code:
- A cluster now validates itself the moment it's constructed (and again on any later change) — an invalid `RKE2Cluster` can't exist, not just "shouldn't."
- `disable_kube_proxy=True` requires `cni="cilium"` — reject/flag any request combining it with another CNI. This can't be changed later by `update()`.
- `cilium_mtu` only means something with `cni="cilium"` — don't set it for any other CNI, and only set it at all if the user describes a specific network problem (packets between nodes crossing a VPN/tunnel/router) rather than as a default tuning knob.
- At least one node must have `role="server"`.
- Prefer an odd number of server nodes (1, 3, 5, ...) — `create()`/`update()` only *warns* on an even count, it doesn't block, but don't propose an even server count unless the user explicitly asked for it.
- `cni` can't be changed by `update()` on a live cluster, and the original first server can't be removed by `update()` — both require `delete()` + `create()` a new cluster instead.
- `RKE2Backend.create()`/`update()` perform REAL system-level actions (install RKE2 via `curl | sh`, start systemd services, may use `sudo`) once someone actually runs the generated script — `127.0.0.1`/`localhost`/`::1` is not exempt, it still installs real software on the machine the script runs on. This agent only generates and validates the script; it never calls `create()`/`update()`/`delete()` itself.

See `docs/rke2.md` in this repo for the full human-facing reference
(known limitations, parallelism behavior, HA caveats) — this file is the
condensed version scoped to what a model needs to generate a correct
tool call, not the complete picture.
